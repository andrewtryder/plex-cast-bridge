# Persistent state and upgrades

A routine code or container upgrade should not require a new Google Home link. Preserve the existing local `data/` directory, `.env`, and Google subscriber credential file, and keep the existing Cloud Run service configuration, OAuth signing secret and client credentials, Firestore data, and catalog bucket. Deploy an image to the existing service without replacing its environment. Do not rerun first-install provisioning as an upgrade. New refresh tokens have no fixed expiry and are revocable through persistent Firestore state. A valid legacy JWT is migrated by hash on first use; that exact token can then remain valid past its embedded expiry. Access-token expiry validation remains enabled. Authorization-code exchanges are retry-safe for the same signed code during its short validity window: if a response is lost after persistence, retrying returns the same opaque token, while an older code cannot replace a newer exchange. A transactionally allocated Firestore order prevents Cloud Run instance clock skew from reversing authorization-code order. Firestore stores only a hash of the active refresh token. Relinking should only be needed for an explicit unlink/revocation, credential change, or unrelated Google Home account problem.

For Cloud Run code releases, use `uv run python scripts/cloud_run_upgrade.py` with the existing project, region, service, a digest-pinned image, and a new private `--preflight-file` path. Review the preflight output, then pass the same manifest path to a later `--apply` command. The apply refuses to deploy if the project, service, target image, current image, protected configuration, traffic assignment, or Firestore link identity changed after review. It checks the link flag, epoch, `agentUserId`, catalog version, and catalog content digest before and after the image update and traffic switch. The candidate revision is created with no traffic; only after it is ready and the configuration and link state still match does the helper route 100% of traffic and existing tags to it. Split/canary traffic fails closed for a manual rollout decision. The file contains a local HMAC key and hashes, not plaintext environment values; keep it private and remove it after validation. For LXC, use `scripts/proxmox_upgrade.sh`; it backs up state and checks a protected configuration fingerprint after replacement. Keep the previous digest and backup until health and Request Sync are confirmed.

There is no automatic OAuth credential-rotation operation. If rotation is ever required, treat it as a separately reviewed migration: preserve the current signing and Google client credentials until a replacement link/token is confirmed, then explicitly revoke the old credential. Never rotate credentials as a side effect of provisioning or an image upgrade.

First-time setup and upgrades are deliberately separate. `gcp-cloud-run/deploy.sh` is for a new service only and now stops if that service already exists. The dashboard wizard detects the persisted gateway URL even if `google_home_setup.json` is missing; it treats link state as unknown unless the cloud state confirms it and disables project creation and credential minting for an established installation. Do not use reset or first-install actions to recover or upgrade an existing installation.

The [Cloud Run guide](../gcp-cloud-run/README.md) describes the image-only update. Before an upgrade, back up persistent data and configuration, record the current image and Cloud Run revision, and check rollback availability. Backups contain credentials and should be private.

## Local files

The root `catalog.json` is a tracked seed for new installations and image builds. On Docker installations, the working catalog is `data/catalog.json`, mounted as `/data/catalog.json`; it changes as speakers and library data change. An explicit `CATALOG_PATH` overrides the usual location, so include that path in your backup if configured.

`google_home_sync.json` holds mutable gateway configuration and sync state, including a catalog write credential. It normally lives in `DATA_DIR`, which is `/data` in Docker. Its permissions and backups should be treated as secret. Plex connection credentials, setup state, settings, and the optional [music index](music-index.md) also live under `DATA_DIR` and must survive a container replacement. A legacy `dashboard_sessions.sqlite3` may remain after upgrade; the application no longer uses or deletes it.

Outside Docker, `DATA_DIR` selects the runtime directory. If unset, the application uses `/data` when present, otherwise the repository's `data/` directory when it exists, and otherwise the project root. A root-level `google_home_sync.json` can therefore be active runtime state; do not delete it without checking the configured path and migrating its contents. The project-root catalog can also become mutable under that fallback. Prefer an explicitly configured `DATA_DIR` outside the source checkout for non-container installations.

## Cloud state

The gateway stores catalog objects in Cloud Storage and synchronization/link metadata in Firestore. Google retains the OAuth tokens; the gateway validates them using its signing secret. The local sync file is not a replacement for that cloud state. A successful initial Google SYNC does not prove that later HomeGraph Request Sync calls work: inspect both outcomes separately.

## Configuration authority and drift

Run `python -m plex_cast_bridge.config_drift` inside the production container, or `uv run python scripts/config_drift.py` in a development checkout from the bridge's working directory to inspect local configuration without starting the application. It reports sources and conflicts, never values or hashes, and does not write files, open SQLite, contact Plex or Google, or inspect Cloud Run or Firestore. Run it in the bridge's actual process environment (for Compose, inside the running container) to see the environment the bridge receives. Docker Compose injects the root `.env` through `env_file` and explicitly overrides `DATA_DIR`, `PORT`, and `GOOGLE_APPLICATION_CREDENTIALS`; the process cannot distinguish injected values from other process environment values. Outside Compose, Pydantic reads `.env` relative to the working directory; process environment takes precedence. `DATA_DIR` and `CATALOG_PATH` are read directly from the process environment, so a standalone Pydantic dotenv file does not set those paths. Conflicts identify selected differences among locally observable configured values, not proof of a fault. Unreadable files and remote state cannot be compared; a false conflict flag does not establish remote consistency.

| Configuration | Current authority and compatibility |
| --- | --- |
| Plex server, section and credentials | A saved JWT connection in `plex_connection.json` is tried first; legacy `PLEX_URL`, `PLEX_MUSIC_SECTION`, and `PLEX_TOKEN` remain supported as fallback, including when JWT reconnect fails. Device keys are separate files in the same directory. Do not remove either credential based on a conflict alone; JWT and legacy tokens can differ legitimately. |
| Playback volumes | `app_settings.json` overlays Pydantic environment/default values after a save. Environment values remain bootstrap defaults. |
| Gateway URL and catalog write key | `google_home_sync.json` is used for catalog pushes and pairing. **Current startup behavior:** when both `CLOUD_GATEWAY_URL` and `CATALOG_WRITE_KEY` resolve to nonempty environment/dotenv values, startup copies both over the sync file, even if it already has different values. A partial pair does not override it. The wizard can also update the sync file. Treat the file as the intended persistent owner, but keep this legacy precedence until an explicit backward-compatible migration is designed; do not remove or change credentials to resolve drift automatically. The cloud gateway's configured write key must match the local one. |
| Catalog and speakers | Explicit process `CATALOG_PATH` selects the working file; otherwise `DATA_DIR/catalog.json` is read if present, falling back to the bundled root catalog. Writes normally create the data catalog from the seed. This file owns local speaker identities, toggles, and catalog data; the root catalog is normally a seed. Cloud Storage holds uploaded catalog snapshots and Firestore tracks the active version and link metadata. They may temporarily differ during sync. |
| Google Home setup | `google_home_setup.json` is resumable wizard history and a record of project/URL; it is not proof of current cloud link state. The sync file controls local gateway requests. Firestore controls cloud linkage and stable identity; Google holds its OAuth tokens. |
| Music index | `music_index.sqlite3` owns index-specific enabled/schedule/AI settings, scan state, derived metadata and mixes. It is not the authority for Plex credentials, the catalog, gateway settings, or general application settings. No migration of those settings to SQLite is implied. |
| Infrastructure and cloud credentials | Process environment remains the current source for subscriber project/subscription, listener enablement, service-account credential path, Gemini key, discovery intervals and other non-UI settings. Cloud Run environment/secret bindings own gateway OAuth client credentials, signing secret, admin credential, API keys, project/topic/bucket and deployment options. Firestore owns durable link, refresh-token and synchronization state; Cloud Storage owns cloud catalog objects. Preserve all of them across upgrades. The local diagnostic cannot verify them. |

Pydantic also accepts `LOCAL_API_KEY` and `ALLOW_UNAUTHENTICATED_LOCAL_API` as legacy settings; access is controlled at the network layer. Defaults and complete environment field names are defined in `src/plex_cast_bridge/config.py` and `gcp-cloud-run/src/cloud_gateway/config.py`. Wizard values are historical hints and may be stale. Do not run provisioning, relink, or edit `.env` or persistent state merely to make the diagnostic report no conflicts.

For an LXC/Docker upgrade, update the helper and source checkout first, then run `bash scripts/proxmox_upgrade.sh config-preflight` in the deployment environment. It uses the running container's environment and mounted data and can inspect an older image before the module is packaged there. Review any `release_preflight_warnings`: both environment values are present and at least one differs from the sync file, so startup will overwrite it. A difference with only one environment value is informational. The upgrade stops on these warnings unless the operator explicitly sets `ACK_CONFIG_DRIFT=1` after review. A missing diagnostic stops the upgrade. The helper stores redacted `config_drift_before.json` and `config_drift_after.json` alongside its backup; an unavailable or invalid post-upgrade report leaves acceptance NOT TESTED and returns a nonzero exit code. The Cloud Run image-only helper reports cloud configuration and Firestore fingerprints separately; it cannot inspect the local bridge environment or compare its secrets with Cloud Run.

Only explicitly saved volume keys are compared for drift; the application may normalize missing keys to defaults when loading a nonempty settings file. Plex JWT and legacy token values are separate compatible credentials and are not conflicts. Environment precedence and wizard history are shown as sources, not automatically treated as failures.
